> 调研日期：2026-06-14
> 调研范围：`lib/search/query-rerank.ts`、`lib/server/catalog-repository.ts`、`data/huqifeng-test-queries.json`、README、`.issues/`
> 目的：理清现有权重体系的全貌，识别问题，为改进方案提供依据。

## 一、体系全貌

### 1.1 两条重排路径

| | 默认重排 `computeBookScore` | 轻量重排 `applySimpleRerank` |
|---|---|---|
| 位置 | `lib/search/query-rerank.ts:250-440` | `lib/server/catalog-repository.ts:222-262` |
| 行数 | 187 行 | 40 行 |
| 触发条件 | 候选数 ≤ 500 | 候选数 > 500 |
| 加权项 | 27 处 `score +=/-=` | 4 处 |
| 领域规则 | 有（健康/科学/棋类/鲁迅/历史/年龄） | 无 |

**切换阈值**：`catalog-repository.ts:184` 的 `SIMPLE_RERANK_THRESHOLD = 500`。

**关键事实**：用户选 100 本时，召回候选 = `100 × 4 = 400`（≤500，走默认重排）；选 200 本时，召回候选 = `200 × 4 = 800`（>500，走轻量重排）。即**200 本档位下所有领域规则和排除词惩罚全部失效**。

### 1.2 词项来源差异

| | 默认重排 | 轻量重排 |
|---|---|---|
| 词项来源 | LLM/规则解析的结构化 `requirement.keywords` | 从原始 query 现场正则分词 + 停用词过滤 |
| 精度 | 高（经过需求分析 Agent 处理） | 低（粗粒度切词） |

## 三、发现的问题

### 问题 1：权重数值量级混乱，无标定依据 ⚠️ 严重

所有权重数值是**人工拍脑袋**的，没有基于评测数据标定。量级分布极不均匀：

```
鲁迅命中:     +20    ← 是分类整体匹配(+4.5)的 4.4 倍
排除词:       -10    ← 是零命中惩罚(-2.75)的 3.6 倍
分类匹配:     +4.5
棋类命中:     +4.5   ← 与分类匹配同级，但语义完全不同
年龄适配:     ±3.0
健康主题:     +2.2
科学主题:     +1.8
标题+健康:    +0.9   ← 与标题命中(3.5)量级不搭
```

**具体后果**：鲁迅 +20 能单枪匹马碾压一切。一本和查询毫无关系、流行度为零的书，只要书名/简介含"鲁迅"，就能 +20，把标题完全命中、分类完全匹配（最高 ~4.5+3.5×N）的书挤下去。

### 问题 2：硬编码规则对用户不透明 ⚠️ 中等

用户在 UI（TuningPanel）只能调两个滑块：「分类权重」和「关键词权重」。但背后还有 12 项主题特化规则在影响排序，用户**完全看不到也调不了**。

规则触发条件是 8 个写死的正则模式（健康、科普、象棋、围棋、国际象棋、五子棋、历史/传记、鲁迅）。规则之间会叠加甚至冲突，用户无法预期一本书的最终得分。

### 问题 3：大批量场景领域规则全部失效 ⚠️ 严重

200 本档位走轻量重排，以下规则**全部失效**：
- 排除词惩罚（−10）—— 用户明确设置的"排除教材"约束被忽略
- 年龄/馆别适配（±3.0）—— 小学/初高中馆别下年龄不符的书混入
- 分类整体匹配（+4.5）—— 相关性下降
- 零词命中惩罚（−2.75）—— 完全不相关的书不被压低
- 所有主题微调

这是**用户体验断层**：用户选了排除词，小批量时生效，大批量时静默失效。

### 问题 4：词项来源不一致导致轻量重排质量下降 ⚠️ 中等

默认重排用 LLM 解析的结构化 `requirement.keywords`，轻量重排用原始 query 现场正则分词。两者精度差异大，但用户无从感知切换发生。

### 问题 5：棋类互斥逻辑过于冗余 🟡 轻微

4 种棋类 × 2 方向（命中/互斥）= 8 条几乎相同的代码（行 344-376），每个棋种单独写一份。如果将来新增棋种（如跳棋、军棋），需要再加 2 条。

### 问题 6：规则缺乏测试覆盖 🟡 中等

`tests/agents.test.ts`（25 个用例）测试了部分重排逻辑，但：
- 主题特化规则的触发边界（正则精度）未系统测试
- 权重叠加/冲突场景未测试
- 轻量重排的 4 项加权几乎无测试

## 四、测试集与规则的对应关系

`data/huqifeng-test-queries.json` 包含 10 条标准查询：

| 查询 | 对应的硬编码规则 |
|---|---|
| psychology-growth（心理成长） | 无直接对应规则 |
| travel-city-culture（旅游城市） | 无直接对应规则 |
| **history-biography（历史传记·鲁迅）** | HISTORY_PATTERN + LUXUN_PATTERN |
| **health-popular（健康养生）** | HEALTH_PATTERN |
| **chess-xiangqi（象棋）** | XIANGQI_PATTERN + 互斥 |
| **go-beginner（围棋）** | WEIKI_PATTERN + 互斥 |
| public-admin（公共管理） | 无直接对应规则 |

## 五、改进方案对比

### 方案 A：最小修复（仅补轻量重排）

**做什么**：给 `applySimpleRerank` 补上排除词惩罚 + 年龄适配两项高价值规则。

| 维度 | 评价 |
|---|---|
| 解决问题 | 问题 3（大批量失效） |
| 工作量 | 低（~40 行） |
| 风险 | 低 |
| 缺点 | 硬编码和量级问题原封不动 |

### 方案 B：规则外置为配置（中等工作量）

**做什么**：
1. 先做方案 A
2. 把主题特化规则（8 个正则 + 12 项加权）从代码搬到配置文件（如 `config/rerank-rules.ts` 或数据库表）
3. 管理后台可见可调

| 维度 | 评价 |
|---|---|
| 解决问题 | 问题 2（不透明）+ 问题 3 |
| 工作量 | 中（~200 行 + 后台 UI） |
| 风险 | 中（需回归测试） |
| 缺点 | 权重数值仍靠人工标定，鲁迅 +20 的问题不变 |

### 方案 C：砍掉特化规则，回归通用打分（激进）

**做什么**：
1. 先做方案 A
2. 删除所有主题特化补丁（鲁迅 +20、棋类互斥、健康/科学/历史微调）
3. 只保留：字段命中 + 分类匹配 + 排除词 + 年龄适配 + 反馈

| 维度 | 评价 |
|---|---|
| 解决问题 | 问题 1（量级）+ 问题 2（透明）+ 问题 3 + 问题 5（冗余） |
| 工作量 | 中（删除代码 + 回归测试） |
| 风险 | 中-高（鲁迅/棋类等特定查询质量可能下降） |
| 缺点 | 牺牲边缘场景精度，需验证测试集是否仍通过 |

### 方案 D：评测驱动的权重标定（重）

**做什么**：
1. 先做方案 A
2. 基于现有 `huqifeng-test-queries.json` 建立自动化排序质量评测
3. 用评测数据反推合理权重（如网格搜索/手动迭代）
4. 可选：方案 B 或 C 作为落地形式

| 维度 | 评价 |
|---|---|
| 解决问题 | 问题 1（量级）根治 + 问题 6（测试） |
| 工作量 | 高（评测框架 + 迭代标定） |
| 风险 | 低（数据驱动，可回溯） |
| 缺点 | 周期长，需要人工标注或扩展测试集 |

## 六、推荐路径

**分阶段实施，每阶段独立交付价值**：

| 阶段 | 方案 | 目标 | 建议 |
|---|---|---|---|
| **阶段 1** | 方案 A | 修复大批量即时问题（排除词/年龄失效） | ✅ 立即做 |
| **阶段 2** | 方案 D 的评测部分 | 建立排序质量评测，量化现状 | ✅ 接着做 |
| **阶段 3** | 方案 B 或 C（看评测数据决定） | 根据评测结果选择外置或砍除 | ⏸ 看数据再定 |

**理由**：
- 阶段 1 解决明确的用户痛点（大批量排除词失效），低风险高收益
- 阶段 2 提供决策依据——在没数据的情况下争论"鲁迅 +20 合不合理"是空谈，有了评测就能用数字说话
- 阶段 3 的方向选择（保留规则但外置 vs 直接砍掉）依赖阶段 2 的评测结论
