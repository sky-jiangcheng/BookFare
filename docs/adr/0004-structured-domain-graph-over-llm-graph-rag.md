# ADR-0004：多跳关系用结构化领域图谱，而非 LLM 实体抽取（L3）

- 日期：2026-10-31
- 状态：🔵 Proposed（待确认）

## 背景

现有重排规则已出现"实体定向"需求（鲁迅专题 +20、历史传记 vs 小说区分、棋牌互斥惩罚等），本质是**多跳关系查询**："找鲁迅的传记，但不要小说化的演义"。用户希望获得 Graph RAG 的多跳能力，但已确认：

1. Microsoft GraphRAG 索引成本约为向量 RAG 的 100 倍（一本 3.2 万词书 $4-7，GPT-4o），查询为语料级全局搜索，与图书推荐的实体级查询模式不匹配
2. LightRAG 虽便宜 3-5 倍，仍需对每本书简介跑 LLM 实体抽取
3. **图书数据天然高度结构化**：作者、分类、CLC 分类号、年龄段、系列、关键词字段已存在于 `books` 表——领域图谱可以从这些字段**确定性构建**，不需要 LLM

## 决策

在 Postgres 内构建确定性领域图谱，用递归 CTE 做多跳查询，不引入图数据库和 LLM 抽取：

1. 建表 `book_edges(from_book, to_book, edge_type, weight)`，边类型包括：`same_author`、`same_series`、`same_category`、`same_clc`、`same_age_band`、`topic_entity`（如"鲁迅"从书名/作者字段直接抽取的实体标签）
2. 实体标签来自结构化字段匹配 + 现有 `library_categories` 关键词表（`app/api/admin/library-categories` 已有管理界面），**零 LLM 成本**
3. 查询侧：命中实体/分类后，用递归 CTE 取 1-2 跳邻居加入候选池，交给现有重排打分（新增 `S_graph` 子项）
4. 数据更新：导入/重分类脚本同步重建受影响节点的边，无需全量重建

## 备选方案（被否决/延后）

| 方案 | 结论 |
|---|---|
| Microsoft GraphRAG | 否决：成本高 2 个数量级；全局社区摘要解决的是"语料主题理解"，不是"找哪本书" |
| Apache AGE（Postgres 图扩展） | 否决：Neon 不支持该扩展 |
| LightRAG（见 ADR-0005） | 延后：仅在结构化图谱无法覆盖模糊实体关系时启用 |
| 独立图数据库（Neo4j/Memgraph） | 否决：万级节点规模下递归 CTE + B-tree 完全够用，LightRAG 官方也承认 AGE 后端在生产中不如 Neo4j，但我们的规模连这一步都到不了 |

## 后果

- 正面：零 LLM 索引成本；零新增服务；图谱可解释（每条推荐理由可追溯边类型）；与现有 admin 管理界面天然衔接
- 负面：只覆盖结构化字段能表达的关系，无法发现简介里隐含的跨领域关联（这正是 LightRAG 备选存在的意义）；`book_edges` 需要维护与 `books` 的一致性
- 预估规模：5 万本书 × 平均 5 条边 ≈ 25 万行，递归 CTE 1-2 跳查询在毫秒级
